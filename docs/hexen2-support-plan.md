# Complete Hexen II support through Quaked’s existing engine

Status: **PLAN APPROVED for design completeness** after the second independent architecture and verification review on 18 October 2026, including the paired UQE references. Both review rounds and their evidence limits are recorded in section 10. This is a plan updating gate: only planning documents and their input inventories may change. No implementation, test authoring, build, merge, or release is authorised by this review itself.

## 1. Requirements and delivery contract

The result is native Hexen II support inside Quaked’s existing product: complete base and Portal of Praevus campaigns, genuine demo support, all supplied-edition classes and gameplay, Classic and Enhanced presentation, every existing Quaked enhancement or a newly created Hexen counterpart, the entire pinned jsHexen2-progs fix set, persistent single-player hubs/saves, and host plus three remote players over existing native LAN co-op/deathmatch.

| Requirement | Required implementation and acceptance |
| --- | --- |
| Maximum reuse and smallest sound changes | One JavaScript/TypeScript engine, interpreter, renderer, mixer, command/input stack, and enhancement implementations; the existing Rust native shell remains a narrow platform adapter. No second engine, native Hexen executable, parallel launcher, alternate transport, or rewrite of monsters/weapons into JS. |
| Base, expansion and demo | Public IDs `hexen2`, `hexen2-portals`, `hexen2-demo`. Base supports the four retail classes; Portal supports those four plus Succubus. Demo follows its native class/content restrictions. Each edition must work with unavailable editions physically excluded from its fixture root. |
| Native compatibility | Run compiled HCode as game data through the shared JS interpreter. Support original installed gamecode and the corrected builds described in section 4. Development-time HCode compilation does not introduce a C game engine into the shipped application. |
| Both presentation modes | Classic preserves native presentation and native rules except explicitly selected corrected gamecode. Enhanced adds the complete parity set in section 7. Gamecode choice and graphics quality are separate, visible settings. |
| All reference improvements | Every change in the pinned reference catalogue has a numbered behavioural/provenance record and an acceptance assertion in the [review input inventory](hexen2/plan-inputs.json). No fix disappears because its broader family has a test. |
| Every Quaked enhancement | The source inventory covers this dirty checkout and the delivered `Dev` feature set, not only the modules present in this checkout. All feature families and new counterpart defaults are specified in section 7. No `not applicable` closure for a Quake-specific feature. |

Required failures and missing inputs block qualification. |
| Documentation and acceptance | Architecture/contracts, provenance/licenses, feature/fix coverage, trial instructions, failure/recovery instructions, measurements and exact receipts ship with each increment. Native desktop is the Hexen delivery target, retaining the currently documented macOS 14+ and universal arm64/x86_64 packaging contract. Source-browser harnesses may load explicitly served owner files for verification. Published web builds retain their current Quake shareware product and receive no native filesystem authority, purchased Hexen files, or automatic Hexen demo redistribution. Original Hexen/HexenWorld server interoperability, third-party Hexen mods, OEM editions, obsolete pre-1.11 data and importing/exporting external-engine `.sav`/`.gip` saves are outside this compatibility contract; identify them accurately rather than treating them as a broken supported installation. Native demo playback for the supported game protocols remains included.

The [plan input inventory](hexen2/plan-inputs.json) records the reviewed source refs, relevant file hashes, every local/Dev enhancement module, available switches, existing test and trial filenames, and actual owned PAK/gamecode identities. The 159 local enhancement modules and 192 Dev modules differ materially: 33 Dev-only modules include recent environmental, sound, controller and material effects. HEAD alone is not the starting product identity.

Before feature code, independently reconcile the reviewed source against the active resource/distribution work: preserve staged, unstaged, untracked, ignored, parked and evidence material; record a recoverable patch/file manifest; select an isolated `codex/` branch containing the agreed current product inputs. Do not reset/stash the shared checkout, overwrite another lane, automatically merge a parked branch, or substitute old HEAD assets. Changes since this inventory require a documented delta and amended coverage before they enter the implementation candidate. The resulting exact source tree plus asset manifest becomes the baseline for RED/GREEN and performance evidence.

Reuse is justified by existing contracts: `desktop.js` already routes native discovery into the shared catalogue and canonical PAK parser; entity/global accessors already isolate script data from server callers; hooks install one enhancement implementation; existing hub snapshots serialize globals/entities/resources; and LAN already transports the engine’s messages. Extend those boundaries. New code is limited to proved missing formats/semantics, profile-specific bindings, transactional hub persistence, native loose-file metadata/access, and verification orchestration. A new subsystem requires a written reason why an existing boundary cannot cover it.

Use the existing `assets/layout.json`, resource-path resolver, distribution manifest, prepared-data caches/workers and asset URLs. Do not recreate root `newer/`, `maps/`, `music/`, a parallel asset tree, or another cache/downloader. New art and gamecode outputs enter existing inventories with game-family and native-content identities. Prepared data for Quake must never match a Hexen texture/model on name alone.

## 3. Session, loading and native platform interfaces

### Session descriptor and lifecycle

Extend the current catalogue/selection interfaces with a validated session descriptor containing game ID/family, edition, content root identity, gamecode mode/digest, script-layout version, protocol family/version, rules mode and simulation-affecting feature values. Construct it before mounting or `Host_Init`, then hold its simulation identity immutable until a new game/reload. Reuse reload-based unmounting for game, edition or gamecode changes so model, sound, palette, script and picture caches cannot leak between games.

Gamecode choices are **Corrected** (default for new Hexen runs) and **Installed** (explicit compatibility/reference mode). The new-run menu selects a **Classic rules preset** or **Enhanced rules preset** and labels it separately from graphical controls. Presets change only when starting a new run or loading a save with its recorded preset; choosing another preset during play requests a new run rather than changing the current world. Installed gamecode uses its native gameplay rules and disables gameplay-changing enhancements visibly. Corrected Classic has the approved reference corrections without Enhanced additions; Corrected Enhanced additionally enables the optional SP rules in section 7. HDR, rendering quality, split comparison, resolution and graphics fallback remain presentation-only: an Enhanced run rendered with classic graphics still displays “Enhanced rules”. No rendering toggle, classic comparison pass or menu changes server rules. Changing any other simulation-affecting setting likewise requires a new run; loading restores the complete recorded rules descriptor.

Select family-specific startup scripts, registration detection, palette/colormap/tint tables, fonts, menu pictures, class selection, HUD, level offers and attract demos. Never mount Quake’s rebuilt start map or infer Hexen support from `!missionMounted`. Do not auto-fallback from a selected invalid Hexen game to Quake. Show the shelf with the actual failure and preserve existing saves/settings.

### Discovery, precedence and bounded loose files

Support selecting `~/quaked`, a complete `Hexen 2` installation, its `data1` directory, or the supplied separate Portal installation layout. Match known nested aliases case-insensitively. The complete installation’s sibling `portals` is preferred for its expansion entry; the separate `Hexen 2 Portal of Praevus/Data/portals` is a distinct source candidate, never silently merged with it. Show the resolved source in the shelf. If an explicitly chosen candidate is invalid, report it rather than substituting a different candidate. Identical archives may be deduplicated for reads, but differing loose `progs.dat` files remain distinct installations.

For supported Hexen directories, probe `pak0.pak` through `pak9.pak` independently across gaps. Search order is: selected corrected gamecode overlay for its approved program outputs only; expansion loose files; expansion PAKs in descending number; base loose files; base PAKs in descending number. Installed mode omits the corrected overlay. This follows the pinned Hexen filesystem’s loose-above-PAK and expansion-above-base semantics. Keep Quake’s existing behaviour unchanged. Optional shipped art is resolved separately and cannot shadow native gamecode, maps, strings, configs or puzzle data.

Reuse native opaque file tokens and range reads; the frontend never supplies arbitrary host paths. Enumerate only engine-recognised files in the selected root and known `maps`, `models`, `gfx`, `sound`, `music` and `midi` subtrees. Ignore executables, installer containers and GL driver caches. Enforce canonical-root containment for directories and every opened file; reject traversal, case-folded duplicate names, escaping symlinks, invalid ranges and changed files. Recheck identity around reads and invalidate the scan generation on root changes. Reuse existing PAK bounds and 128 KiB metadata reads; retain format-specific payload/count limits and bounded asynchronous asset loading. No directory walk, IPC, file hashing or disk read is introduced into a per-frame hot path.

Resolve root-level gamecode and text dependencies before synchronous engine loading. Load other dependencies through the existing async/precache boundary, caching resolved logical bytes in the same search path. Verify a stable effective-file manifest before play and before LAN admission. Include PAK and effective loose simulation files, map corrections and selected gamecode in save/LAN identities; exclude private absolute paths and presentation-only preferences from network fingerprints.

### Edition detection and supported assets

Use native content/header/directory signatures and required file manifests, not folder labels or Quake’s `gfx/pop.lmp` check. Derive `registered`, `oem`, class availability and campaign routing from the validated edition; users cannot unlock retail progression by editing archived settings. Support retail 1.11, Portal 1.12 assets, and the November 1997 demo v1.11. The pinned upstream demo signature is 797 entries, directory CRC 22780 and 27,750,257 bytes; verify the full archive hash and licence from its acquired source before its RED tests. Mixed editions fail explicitly. Existing user files are never patched in place; old data receives instructions to prepare a supported copy.

The supplied Shareware directory is Heroes II data. A genuine demo fixture is currently absent. Acquiring and verifying it is a mandatory test-input prerequisite owned by this implementation, not a request to infer demo support from retail `demo1.bsp`.

### Paired UQE comparison and minimal-change policy

The UQE engine trees share 107 `.c`/`.h` relative filenames and several identical normalised core function bodies. That makes them a useful side-by-side change locator, not an estimate of effort or proof that any C file is portable unchanged. For each touched subsystem, compare the paired functions and callers, identify what Quaked already implements, and port only the independently verified missing Hexen semantics into that existing JS boundary. Preserve the reusable algorithm and give format/layout/calling-convention differences explicit profile parameters. A second implementation requires proof that this adaptation cannot work.

Native Raven contracts and supplied supported assets define Installed compatibility; pinned jsHexen fixes define requested corrections; selected Enhanced rules define deliberate new behaviour. UQE differences are candidates to evaluate under those contracts, not another source of automatic gameplay changes. Record each consulted/accepted/rejected UQE delta, both source pins and affected public tests in the overlap ledger. Conflicts are resolved at the source-contract level before implementation of that delta.

Do not inherit UQE protocol 20/interoperability, sound-index extensions, raised limits/stacks, vector-magnitude velocity clamping, unfinished switch handlers or its invalid-BSP sentinel workaround. Retain bounded errors rather than partially initialised models, no-op opcodes or limits raised to hide an upstream defect. Keep WebAudio, Three/WebGL and the existing native adapter; exclude FMOD, Win32/WGL and unrelated renderer/device integrations. Both trees contain GPL material, but per-file and third-party notices still govern individual reuse. A translated routine retains its provenance and required notices. These comparisons do not add UQE server/demo support or replace the selected corrected gamecode.

Keep base/demo and expansion builds separate. Expansion uses the pinned js source; it cannot serve base-only installs because it precaches expansion replacements and Succubus assets. Base starts from pinned `gamecode/hc/h2` sources, backports each applicable js correction, and reverts unrequested uhexen gameplay/balance changes to the installed Raven 1.11 behavioural baseline. In particular, do not inherit its faster crossbow cadence, changed backstab/holy-strength/full-mana/healing level thresholds, sickle balancing, or rewritten innate cloak behaviour merely because the source compiles. Preserve frame-rate independence while matching the native reference cadence. Native class stats, damage, loot probabilities and progression remain unchanged except the explicitly required js fixes and Enhanced mechanics. Differential script tests against supplied original programs establish this boundary. Expansion retains the deliberate behaviours documented by the chosen js reference.

Maintain one normative record per reference change in `plan-inputs.json`: source commit(s), affected edition, trigger, observable expected outcome, and RED/GREEN test ID. Shared fixes must be present in both applicable builds; expansion-only mechanics are qualified on Portal, not falsely backported to a nonexistent base mechanic. The reference version-reporting change becomes a truthful Quaked/gamecode provenance print; the original import commit is provenance, not a pretend behavioural fix. No silent omission, proxy score or blanket “already covered” entry.

Extend the existing VM for all instructions and builtin contracts exercised by the supported programs, including extended arithmetic/indirection, cycle/weapon state, random and switch instructions, text/puzzle helpers, effect lifecycle, sound position and class functions. Keep typed entity/global access for existing server callers; derive validated offsets/types once from the selected program and keep Quake’s fast path. Hexen CALL1 copies the statement operand `b` vector into OFS_PARM0; CALL2 through CALL8 additionally copy `c` into OFS_PARM1 before builtin/function dispatch. Decode global/data operand indices as unsigned 16-bit while keeping each opcode’s branch displacement signed. Indexed global fetches must check the encoded array bound before reading. Do not reuse Quake’s call-argument assumptions or reinterpret every operand unsigned indiscriminately. T03 includes data offsets above 32767, backward branches, nested calls, both copied arguments and out-of-range fetch controls against an independent oracle. Recognise the supplied base layout CRC 38488 and Portal layout CRC 26905 with definition validation; neither CRC alone nor accepting any CRC establishes compatibility. Check section bounds, statement/function indexes, vector widths, entity pointers, string offsets and builtin numbers before use. Unsupported instructions/builtins produce a bounded script error with function/statement and gamecode identity; they are never no-op success. Preserve runaway/stack guards and ensure nested calls restore interpreter and enhancement observer state after exceptions.

Use the pinned upstream `hcc` as a development-only compiler in isolated outputs. Version and hash its source, binary, flags and build inputs; retain save-layout-compatible compiler flags for base sources and test expansion optimisations against its declared layout. Produce deterministic `progs.dat` outputs and compare clean rebuild hashes. Source, licence notices, patches and reproducible build instructions accompany distributed gamecode; purchased PAKs do not. Build generation fails if a program/layout/asset manifest differs from its recorded output. Runtime use is offline; no compiler, native Hexen engine or source download is needed on the owner’s Mac.

## 5. Shared simulation, formats, protocol and presentation

Reuse BSP29 geometry parsing with Hexen’s eight-hull submodel layout and native class/entity hull selection; do not assume the shared version number implies Quake’s 64-byte submodel record. Extend IDPO/RAPO, sprite, skin/group-frame, transparency, palette/tint, scale/origin, absolute-light and drawflag handling within existing model structures. Preserve native animation/collision/model bounds and material identity. Validate counts, finite transforms, indexes and lump ranges before allocation. Native brush movement, rotating bounds, crouch/jump/fly/swim, pushers, missiles, bounce and polymorph use authoritative Hexen semantics.

Protocol messages cannot share Quake’s decoder switch: Quaked messages 42/47/48/49 collide with Hexen effect/reference/clear/inventory messages, and client command 5 also differs. Select the protocol family before decoding any body. Retain Quake 15/1015 unchanged. Use an explicitly private Quaked-Hexen session protocol number 1019, versioned as `quaked-hexen2-v1`, over existing loopback/Window/native TCP transport; it carries native Hexen message semantics and a separately length-bounded Quaked extension envelope at service opcode 63 for existing Quaked additions. Record this as private, not an interoperable Raven protocol. Do not emit Quake prediction/delta opcodes into Hexen streams. Keep legacy Hexen demo decoders for native 18/19 separate from the private live protocol, with playback-only state and no live server/rules mutation.

Cover native baselines, model/sound index widths, inventory/stat masks, class/colour, scaling, alpha/light flags, view flags/tint, intermissions and all effect create/update/end messages. Truncated or unknown message bodies disconnect only the offending peer/playback with diagnostics; never guess a payload length or continue desynchronised. Large effects obey both the selected engine channel/message budget and the existing 65,536-byte native frame ceiling; chunk reliable signon state with explicit bounds rather than dropping inventory or increasing unbounded buffers. Test maximum supported map/sound/entity counts against the chosen codec.

Reuse existing menus/input and add native class selection, four class-weapon slots, inventory previous/next/use, puzzle/objective display, difficulty, level offers, and gamecode/mode labels. Keyboard/mouse, controller wheel/bindings and existing touch controls must drive these same commands; focus/menu close/paused/held-button changes cannot fire or consume artifacts accidentally. Class abilities, level/experience/max-health/mana, armour pieces, artifacts/rings and all powered weapon variants use native game state, not Quake item-bit guesses. Support class-specific fonts, HUD and cutscene text without relying on Quake pictures being present.

Audio uses the existing WebAudio context, spatializer and SFX/music buses. Implement native sound-position/stop/channel semantics and map music commands; prefer installed CD-track/OGG/MP3 equivalents where present. Native MIDI fallback uses a bounded JS MIDI type 0/1 event decoder and General MIDI voice scheduling into the same audio context; no OS player or second mixer. Its procedural fallback voices and native sound effects require audible comparison and owner acceptance. Audio unlock refusal is reported/retried on the next user gesture without blocking gameplay. Missing optional music remains a visible content issue; required sound/effect support cannot be declared complete by muting it.

### LAN rules

Host owns time, damage, inventory, puzzle/cross-trigger state, class validity, entity/effect creation and hub transitions. Peers negotiate the private protocol, effective content/gamecode identities and simulation feature settings before signon; mismatches fail before joining. Class changes follow native rules, not arbitrary client edits. Gameplay-changing Enhanced additions stay single-player-only for this delivery, matching their existing Quaked restrictions; native co-op/deathmatch plus client-side visual/audio enhancements remain fully supported. Show that limitation in the host/options UI and lock server-affecting choices for the session.

A late join receives the host’s current world/inventory/puzzle/effect baseline before movement admission. Rejoining uses native new-player/spawn semantics; disconnect drops follow native gamecode and no remote inventory is resurrected by name. Active clients retain their own state across host-coordinated hub transitions. Prepare the next map/resources and check capacity before committing the transition; a missing resource or failed client load ends that join or keeps the party on the previous committed hub, with a clear reason. Clients cannot redirect the host through a supplied map string. Host departure ends the session; no implicit host migration or co-op save system. Single-player save/load commands reject LAN sessions clearly and leave the session untouched.

## 6. Whole-hub persistence and failure recovery

Reuse serialization primitives, with Hexen archive semantics: separate world and player records, respect `FL_ARCHIVE_OVERRIDE`, preserve startspot and cross-trigger flags, restore player stats/`ClientReEnter`/`RestoreClients` behaviour, and serialize persistent non-edict effects plus resource names. Retire a previous hub when native progression does so. Preserve timers using saved server time and the native paused/unvisited-map rules; do not age or reset them from wall-clock time or a rendering toggle. Rebuild transient entities through native callbacks instead of duplicating archived temporary entities. Restore model/sound identities by logical name and validated content, not old cache indexes.

The current one-value localStorage save cannot safely hold whole hubs. Introduce one shared async save repository at the existing save/load boundary using platform IndexedDB transactions; retain legacy Quake localStorage reads/writes through an adapter without migrating or deleting its keys. This is persistence plumbing, not a separate native service. Extend the existing save/load menu and console completion handling for async busy/error states.

Version-1 Hexen save bundles contain metadata, profile/gamecode/rules identity, slot summary, active player/world, visited-level snapshots, persistent effects and enhancement records. One readwrite transaction commits slot contents and summary together; an aborted/quota-failed write leaves the previous slot intact. Request storage persistence and report whether the platform granted it; do not claim permanent retention solely because a write succeeded. Keep the last committed slot until its replacement is acknowledged. A new app/frontend version uses the same persistent origin/database identity.

Load in phases: read and structurally validate the complete bundle; verify edition/gamecode/rules and all referenced resources; resolve required assets; capture the current session recovery bundle; suspend simulation/input; restore through the shared engine; validate native postconditions and derived effects; then expose the new session. Preflight errors leave the current world untouched. A runtime restore exception rolls back through the captured bundle and rehydrates previous caches/state. If the graphics/context cannot recover, retain both the previous committed save and recovery bundle and return to the menu with retry instructions; do not overwrite them or report success. Failed loads must not leave a changed skill/class/config, mixed program globals, dangling audio or partially installed level state.

Cover storage denial, quota exhaustion, transaction abort, process termination during save, corrupt/truncated bundle, unsupported schema, changed program/rules, missing map/assets, partial restore, cancelled load, concurrent save requests, app restart and origin/storage upgrades. Serialize save/load/travel operations; a second conflicting operation receives a busy result. In-memory travel remains possible if storage is unavailable, but the UI explicitly says persistence failed and the delivery save gate remains unsatisfied. External Raven save import/export is not silently advertised.

## 7. Exhaustive enhancement parity defaults

The following bindings are design defaults for this port, including genuinely new counterparts; they are not claims that Hexen shipped these mechanics. All rows are required, use shared Quaked algorithms and existing feature controls, and require positive/negative, disabled, pause, reset, save/reload and cross-game tests. Every reviewed module in the input inventory is assigned to a row; support-only modules inherit the owning row’s tests. The implementation must not replace this with a family-level completion percentage.

Visual/audio rows apply when enhanced graphics are enabled in SP or LAN, with no simulation mutation. Rows marked **SP rules** apply only to a Corrected Enhanced-rules single-player run and are independent of whether its current graphics settings use HDR or a classic comparison pass. All such records persist in the hub bundle, while transient GPU/audio/particle handles are recreated. Cosmetic fallback to native assets protects a running trial but does not qualify a missing required counterpart.
